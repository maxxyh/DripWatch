# Supabase sync architecture

## Current deployment

- Hosted project: `DripWatch`
- Project ref: `jasvndjjzimqiidffwfa`
- Region: Singapore (`ap-southeast-1`)
- Swift SDK: `supabase-swift` pinned to `2.46.0`
- Database source of truth: `supabase/schemas/dripwatch.sql`
- Tables: `beans`, `brews`, `bean_photos`, `grinders`, `lexicon_terms`
- Private buckets: `bean-photos`, `brew-photos`

The app uses a modern Supabase publishable key. Publishable configuration is expected to ship
in a client; authorization belongs in RLS. A `service_role`, secret key, database password, or
backup connection URL must never be compiled into the app or committed.

The Next.js PWA under `web/` keeps the URL and publishable/legacy anonymous key server-side and
proxies notebook and private-photo access through signed-passcode session routes. Embedded
`Recipe`, `Pour`, `Taste`, and `TasteBalance` JSON retains Swift `Codable` camelCase keys; table
columns remain snake_case. Reads paginate in stable 500-row pages. The browser never receives a
Supabase key or direct Storage URL.

Pourover `Recipe` JSON includes the optional `dripperName`. It is embedded recipe data (including
pending plans), not a new relational table, so adding or clearing it travels through the existing
brew/bean row last-writer-wins behavior without a schema migration.

## Security boundary

This is deliberately a **no-auth shared-notebook prototype**. The `anon` role can select,
insert, and update every DripWatch row and object; no hard-delete grant exists. Anyone who
extracts the URL and publishable key can read or alter the notebook. This is acceptable only for
the current hobby scope. Add authentication, ownership columns, and ownership-scoped RLS before
wider distribution or sensitive use.

The web passcode protects the interface but is **not a complete Supabase security boundary**.
Anonymous policies remain because iOS depends on them, the passcode provides no per-user
permissions, and offline snapshots reside on the device. Migrate both clients to authenticated
notebook membership and ownership-based RLS, then revoke anonymous grants, before sensitive or
multi-tenant use.

All exposed tables have RLS enabled and explicit grants/policies. Storage policies are scoped to
the two private buckets. Keep SELECT + INSERT + UPDATE for Storage because object upsert requires
all three. Run Supabase security and performance advisors after every DDL/policy change.

## Data and conflict model

- UUIDs are generated by the client and remain stable across SwiftData and Postgres.
- `updatedAt` drives row-level last-writer-wins; `deletedAt` propagates soft deletion.
- A database trigger ignores an older update and rejects timestamps more than ten minutes in the
  future, preventing stale clients or a far-future timestamp from permanently winning.
- Parent rows are pushed before child rows so `bean_id` foreign keys remain satisfiable.
- Pulls are full, stable-ID ordered, and paginated in batches of 500; this avoids PostgREST's
  default row limit. A later pull recovers rows inserted during offset pagination.

Last-writer-wins is row-granular, not field-granular. Two people editing different fields of the
same row concurrently can still overwrite one another. Revisit this before the collaborative web
app becomes heavily used.

Bean purchase value is stored as nullable `price_sgd` and `bag_size_grams` columns. SGD is the
only supported currency; bag size is the labeled net coffee weight. Both values must be positive
when present, and clients derive price per gram rather than persisting a redundant calculation.
Postgres stores price as fixed-precision `numeric(12,2)` and iOS stores integer cents locally, so
currency values never depend on binary floating-point representation.

Swift's synthesized `Encodable` calls `encodeIfPresent` for `Optional` properties, which omits
the key entirely when the value is `nil`. PostgREST's upsert only overwrites columns present in
the JSON body, so a field cleared back to `nil` client-side (discarding a bean's pending
next-brew plan, reopening a finished bean, clearing a bag fact, turning off a brew's plan-next
toggle) would silently fail to clear server-side: the stale value survives the "successful" push
and reappears on the very next pull, even on the same device. `BeanDTO` and `BrewDTO` therefore
implement `encode(to:)` explicitly so every field — including a nil one — is always encoded,
turning `nil` into an explicit JSON `null` that PostgREST does apply. Any future nullable column
that can be cleared after being set needs the same treatment (see
`SupabaseDTOTests.clearedOptionalFieldsEncodeAsExplicitNullNotOmittedKeys`). The web PWA is not
affected — it builds plain JS objects and sends `null` explicitly rather than omitting the key.

Web mutations additionally carry the exact raw `updated_at` originally loaded and conditionally
match both it and `id`. A zero-row update is returned as a stale-write conflict so the editor
refreshes instead of silently replacing a newer iOS or web edit. Inserts cannot overwrite an
existing UUID. This leaves the database's row-level last-writer-wins behavior unchanged for iOS.

Web photo uploads follow the existing 1400px JPEG normalization and lowercase
`<record-id>/<sha256>.jpg` path convention. The object uploads before its row is written. Data API
multi-row flows are not transactional, so idempotent client UUIDs, parent-before-child ordering,
and refresh/reconciliation limit partial-write risk; replaced objects can still be orphaned. A
guarded photo read resolves the record by UUID and serves bytes only when its active row references
the exact canonical path.
The upload proxy independently decodes and verifies JPEG dimensions rather than trusting browser
normalization alone. Offline photo storage retains at most 120 viewed objects and approximately
100 MB for the active signed-session scope.

## Durable synchronization flow

`SyncOutbox` persists pending `(table, id) → generation` entries in `UserDefaults`. A successful
request acknowledges only the exact generation sent, so an edit made while a request is in flight
stays pending. This is intentionally durable across termination and weekly sideload replacement.

`SyncEngine` is MainActor-isolated and permits only one cycle at a time:

1. Snapshot the durable outbox.
2. Push parents, photos, then brews.
3. Acknowledge successfully sent generations.
4. Pull every paginated table.
5. Immediately recheck the outbox before applying each row or downloaded blob so a local edit
   made during network I/O cannot be overwritten.
6. Save SwiftData and schedule another cycle if newer generations remain.

Local mutations debounce for one second. App startup and every foreground transition also sync;
the shelf supports manual pull-to-refresh and shows idle/syncing/failure state.

## First-run bootstrap

Bootstrap direction is explicit:

- **Existing installation:** migrate a legacy `Bean.bagPhoto` into `BeanPhoto` if needed, queue
  every local row, push first, then pull. This seeded the original phone without requesting a
  separate export.
- **Fresh installation:** no local rows are queued, so pull first.
- Mark bootstrap complete only after the durable outbox is empty.

Never replace this with a blind initial pull: doing so can overwrite the only copy of a user's
pre-cloud notebook.

## Photos

Photos do not live in Postgres. `PhotoSync` orientation-normalizes, limits the largest dimension
to 1400 px, encodes JPEG at 0.8 quality, hashes the resulting bytes with SHA-256, and uploads to:

```text
<record UUID>/<content SHA-256>.jpg
```

Uploads use upsert and are idempotent. Postgres stores only the relative path. Pull downloads a
blob when its remote path changed or the local cache is absent. Keep the previous path until a
replacement upload succeeds. Replaced content can leave orphaned objects; cleanup is a future
maintenance task and must be conservative because object deletion is destructive.

## Configuration

`SupabaseConfig` first checks generated bundle keys and then uses the shipped publishable fallback.
The fallback exists because Xcode 16 accepted custom `INFOPLIST_KEY_*` build settings but omitted
those unknown keys from its generated Info.plist. A successful build-setting inspection alone is
therefore insufficient—inspect the built artifact or run the app and confirm network activity.

`Config/Secrets.xcconfig` remains ignored and can override local values. Do not stage it.

## Backups and recovery

Cloud sync is not a backup. `scripts/backup-supabase.sh` creates timestamped logical schema/data
dumps and copies both Storage buckets. It deliberately has no automatic pruning. Configuration,
launchd scheduling, and restore steps live in `supabase/backup/README.md`.

The backup schedule is not active until a private `DRIPWATCH_DB_URL`, absolute backup directory,
and local launchd plist are configured. After setup, perform an immediate smoke backup and verify
the manifest, row counts, object counts, and a representative restored image.

## Verified production seed (2026-08-13)

The physical iPhone seeded 24 beans, 91 brews, 27 bean-photo rows, 4 grinders, 17 lexicon terms,
24 bean images, and 15 brew images. Verification found zero orphaned foreign keys and zero missing
referenced objects. Security advisors returned no findings; the two unused-FK-index notices were
expected on a new database.

Treat these counts as historical evidence, not invariants—the notebook continues to evolve.
